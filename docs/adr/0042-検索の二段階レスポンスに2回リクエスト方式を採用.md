# ADR-0042: 検索の二段階レスポンスに2回リクエスト方式を採用

## ステータス
承認済み

## 背景

作品検索はキャッシュミス時に外部APIでの日本語説明補完が重く、結果表示まで最悪20〜40秒かかっていた。
補完コスト自体の削減（上位20件限定・タイトル単位キャッシュ等）に加えて、
「検索結果をまず即表示し、説明の日本語化を後から反映する」二段階レスポンスを導入することにした。
その実現方式を決める必要があった。

仕様: `docs/superpowers/specs/2026-07-02-search-performance-v2-design.md`

## 選択肢

### A案: 2回リクエスト方式
- **これは何か:** フロントエンドが同じ検索APIを2回呼ぶ。1回目は `enrich=false` で補完をスキップした速報結果を受け取って即表示し、2回目は通常どおり補完込みの結果を受け取って画面を差し替える。
- **長所:**
  - ジョブ基盤・ポーリング・プッシュ配信が一切不要。既存のHTTPリクエスト/レスポンスだけで完結する
  - 実装量が小さく、障害点が増えない
  - 2回目のリクエスト中に生の検索結果を短期キャッシュで再利用すれば、外部API検索の二重実行も防げる
- **短所:**
  - 2回目のリクエスト中、Puma のスレッドを数秒占有する（同時利用者が多いと詰まる可能性）
  - 補完の進捗を細かく通知することはできない（完了時に一括差し替え）

### B案: ジョブ + ポーリング方式
- **これは何か:** 1回目のリクエストで速報結果を返すと同時に補完ジョブを Solid Queue（Rails標準のジョブ基盤）に投入し、フロントエンドが「補完終わった？」と定期的に確認しに行く。
- **長所:**
  - HTTPリクエストを長時間占有しない
  - 補完処理をWebサーバーと別プロセスに逃がせる
- **短所:**
  - EC2（t2.micro）にワーカープロセスの常駐が必要で、メモリ負荷とデプロイ構成変更が発生する
  - ジョブ投入・状態管理・ポーリングAPIの追加で実装量が約2倍になる
  - Solid Queue のワーカーは現在本番で稼働しておらず、運用対象が1つ増える

### C案: SSE / WebSocket によるプッシュ配信
- **これは何か:** サーバーからフロントエンドへ「補完が終わった分から順次」結果を送りつける双方向/一方向のリアルタイム通信。
- **長所:** 補完が終わった作品から1件ずつ画面に反映でき、体感が最もなめらか
- **短所:** Rails APIモード + CloudFront 構成での常時接続はインフラ設定・実装とも複雑さが最大。個人開発の規模に見合わない

## 決定

A案（2回リクエスト方式）を採用する。

## 理由

- Recolly の同時利用者数の規模では、Puma スレッドを数秒占有するデメリットは実害にならない
- B案の最大のコストは実装量ではなくインフラ運用（t2.micro でのワーカー常駐・監視・デプロイ変更）で、
  得られる利点（接続を占有しない）が現在の規模では活きない
- C案は体感最良だが複雑さが規模に見合わない（YAGNI）
- 将来、同時利用者が増えて接続占有が問題になった場合は、APIの外部仕様（`enrich=false`）を
  変えずにバックエンド内部だけをB案へ移行できる

## 影響

- 検索APIに `enrich` パラメータと `enriched` レスポンスフィールドが追加される（後方互換あり）
- フロントエンドの検索フローが「1リクエスト＝1表示」から「速報表示→差し替え」の2段階になる
- 生の検索結果の短期キャッシュ（5分）が増え、キャッシュのキー体系が3種類（フル・raw・タイトル単位）になる
