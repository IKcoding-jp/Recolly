# ADR-0050: 認証エンドポイントのレート制限にrack-attackを採用

## ステータス
承認済み

## 背景
セキュリティ診断（2026-07-22）で、ログイン・パスワードリセット・新規登録のいずれにも
試行回数制限がないことが判明した（診断項目 H-1）。このため以下のリスクがある。

- ログインへの総当たり／クレデンシャルスタッフィングによるアカウント乗っ取り
- パスワードリセットを無制限に叩くことによる、任意アドレスへのメール爆撃

bcryptのストレッチ（`config.stretches = 12`）はオフラインのハッシュ解析を遅くするが、
オンラインの試行回数そのものは制限しない。アプリ層で試行回数を数えて弾く仕組みが必要。

## 選択肢

### A案: rack-attack
- **これは何か:** アプリの入口に立つRackミドルウェア（＝門番）。リクエストをIPやメール
  アドレス単位で数え、一定時間に規定回数を超えたら429で自動的に弾く。お店の入口で
  「お一人様◯回まで」の整理券を配る係のイメージ。
- **長所:**
  - Rails界隈で最も標準的なレート制限gem。情報が多く保守しやすい
  - アプリのキャッシュ（`Rails.cache`）をそのままカウンタに使え、環境ごとの実体
    （本番=solid_cache / 開発=Redis）に追従できる
  - IP単位・メール単位など、エンドポイントごとに細かく制御できる
- **短所:**
  - 依存gemが1つ増える

### B案: AWS WAF（CloudFront）
- **これは何か:** CDN（CloudFront）のエッジでリクエストを検査・遮断するAWSのサービス。
- **長所:**
  - アプリを改修せずインフラ側だけで完結する
  - Railsに届く前のエッジで弾ける
- **短所:**
  - 月額課金が発生する
  - 制御の粒度が粗く、「同一メールアドレスへのリセット試行」のような
    アプリ固有のキーでの制限ができない（IP／地理／レート程度）

### C案: 自前ミドルウェア
- **これは何か:** レート制限ロジックを自分で書いてRackミドルウェアとして差し込む。
- **長所:**
  - 依存gemが増えない
- **短所:**
  - 車輪の再発明。カウンタの競合・期限管理などバグの温床になりやすく、
    セキュリティ機能を自作するのは非推奨

## 決定
A案（rack-attack）を採用する。

カウンタの保存先は `Rails.cache` に委ねる（環境ごとの実体に追従）。
- 本番: solid_cache（PostgreSQL, ADR-0008）。本番にRedisは無いためRedis直指定は不可
  （Redis直指定だと接続失敗でフェイルオープンし、制限が静かに無効化される）
- 開発: Redis（`REDIS_URL`）
- テスト: MemoryStore（Rails.cacheはnull_storeで計数できないため）。かつ既定で無効化し、
  レート制限を検証するspecだけが明示的に有効化する（他specへの副作用を避けるため）

制限対象と初期しきい値（いずれも超過分は429 + JSON `too_many_requests` を返す）:
- `POST /api/v1/login` — IP単位 5回 / 20秒、メール単位 5回 / 60秒
- `POST /api/v1/password`（リセット送信）— IP単位・メール単位とも 5回 / 60秒
- `POST /api/v1/signup` — IP単位 5回 / 60秒

## 理由
- Recollyは個人開発・ポートフォリオ規模で、まず追加コストなしにアプリ層で対策したい。
  B案のWAFは月額課金があり、かつメールアドレス単位の制限という今回の要件を満たせない。
- 総当たり（1IPからメールを変えて試行）はIP単位の制限で、リセットメール爆撃
  （1メール宛に多数IPから試行）はメール単位の制限で、それぞれ別のキーで捕捉できる。
  この使い分けはrack-attackの得意領域で、A案が最も要件に合う。
- アプリのキャッシュ（`Rails.cache`）をそのまま活用でき、本番のsolid_cache・
  開発のRedisに環境ごとに追従する（本番にRedisを新設する必要がない）。

将来トラフィックが増え、エッジでの粗い遮断も必要になった段階でB案（WAF）を
併用する余地は残す（A案とB案は排他ではない）。

## 影響
- `Gemfile` に `rack-attack` を追加。`config/initializers/rack_attack.rb` で throttle を定義。
- 正当なユーザーが短時間に連続失敗すると429になり得る。しきい値は運用を見て調整する
  （初期値は保守的に5回。ロックアウトではなく時間経過で自動解除される）。
- 本番はCloudFront→EC2構成で、trusted_proxies未設定だと `req.ip` がCloudFrontのエッジIPを
  返す。SG（security_groups.tf）でCloudFront以外の到達を遮断済みのため、CloudFrontが末尾に
  付与する `X-Forwarded-For` の実クライアントIPを採用する（`Rack::Attack.client_ip`）。
