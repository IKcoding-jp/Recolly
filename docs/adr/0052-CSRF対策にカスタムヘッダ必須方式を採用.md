# ADR-0052: CSRF対策にカスタムヘッダ必須方式を採用

## ステータス
承認済み

## 背景
セキュリティ診断（2026-07-22）の **M-2** で、CSRF対策の状況を確認した。

Recollyはセッションを **Cookie**（`_recolly_session`）で管理する。にもかかわらず
`ApplicationController` で `skip_forgery_protection` によりCSRFトークン検証を全体で
無効化していた（`csrf_tokens` エンドポイントは用意されているが未使用）。

一方で、実質的なCSRF防御は既に3層存在する。

1. セッション/rememberクッキーが `SameSite=Lax` → クロスサイトのPOST/PUT/DELETEに
   Cookieが送られない
2. CORSは単一オリジン（`FRONTEND_URL`）のみ許可
3. 全リクエストが `Content-Type: application/json` 必須 → クロスオリジンはpreflightで
   CORSに弾かれる

このため実際のCSRF成立難度は既に高いが、多層防御として明示的な対策を1つ加えたい。

## 選択肢

### A案: Railsのトークン検証を有効化
- **これは何か:** サーバーがCSRFトークンを発行し、フロントが状態変更のたびに
  `X-CSRF-Token` ヘッダで送り返して検証する。
- **長所:** 教科書的に正統。既存の `csrf_token` エンドポイント資産を活かせる
- **短所:** フロントの共通fetchラッパーでトークン取得・更新・付与が必要になり、
  全ミューテーションの改修と全画面の回帰確認が必要。回帰リスクが大きい

### B案: カスタムヘッダ必須方式（採用）
- **これは何か:** 状態変更リクエストに独自ヘッダ（`X-Requested-With`）を必須化し、
  サーバーで存在チェックする。ブラウザは非セーフリストヘッダをクロスオリジンで付ける際に
  preflightを要求するため、CORS未許可オリジンは実リクエストを送れない。フォーム送信は
  任意ヘッダを付けられないため、状態変更のCSRFが成立しない。
- **長所:** フロントは共通fetchラッパーにヘッダを1つ足すだけ。回帰リスクが小さい。
  OWASPが推奨するAJAX API向けのCSRF対策パターン
- **短所:** トークン方式に比べると「値の検証」はしない（存在チェックのみ）。ただし
  この方式の安全性はトークンの秘匿ではなく、ブラウザのpreflight/ヘッダ制約に依存するため
  値の検証は本質的に不要

### C案: 現状維持 + 受容の明文化
- **これは何か:** SameSite=Lax + CORS + JSON必須で実害リスクは低いと判断し、コード変更せず
  ADRで受容を記録する。
- **長所:** 変更ゼロ
- **短所:** 多層防御の明示的な1枚が増えない。ログインCSRFや古いブラウザ等の残余リスクが残る

## 決定
B案（カスタムヘッダ必須方式）を採用する。

- `ApplicationController` に `verify_csrf_protection_header!` を追加し、GET/HEAD/OPTIONS以外の
  リクエストに `X-Requested-With` ヘッダを必須化。無ければ403（`code: invalid_request`）
- フロントの共通fetchラッパー（`api.ts` の `request()`）で全リクエストに
  `X-Requested-With: XMLHttpRequest` を付与
- 有効/無効は `config.x.csrf_header_protection` フラグで制御。テストは既定で無効化し、
  専用spec（`csrf_protection_spec`）だけが有効化する（全request specへの副作用を避けるため）

## 理由
- 本アプリはJSON APIで、防御はトークンの秘匿ではなくブラウザのpreflight/ヘッダ制約に依存する
  設計にできる。B案はこの前提に最も素直に合致し、実効性が高い。
- A案は正統だが、全ミューテーション改修と全画面回帰のコスト/リスクが、得られる追加の安全性
  （JSON API + SameSite + CORS が既にある状況では限定的）に見合わない。
- C案は変更が最小だが、多層防御の明示的な1枚を足すという今回の目的を満たさない。

## 影響
- サーバー側で状態変更リクエストに `X-Requested-With` を必須化。正当なフロントは共通ラッパーで
  常に付与するため影響はない。共通ラッパーを通らない直叩き（S3への署名付きPUT等、別ホスト宛）は
  対象外で影響なし。
- 既存の `csrf_token` エンドポイント（`CsrfTokensController`）はこの方式では未使用のまま残る。
  将来A案へ移行する余地として残置する（撤去は別対応）。
- 将来、より厳格なトークン方式が必要になれば、この方式の上にA案を重ねられる。
