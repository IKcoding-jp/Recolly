# ADR-0051: Work画像の認可を投稿者ベースに変更

## ステータス
承認済み

## 背景
セキュリティ診断（2026-07-22）の **M-3** で、Workに紐づく画像（表紙）の認可欠落が判明した。

- Work（作品）は全ユーザー共有で、所有者を表す列を持たない
- 表紙は「最新の画像」が全員に表示される（`Work#resolved_cover_image_url`）
- 画像追加（`POST /api/v1/images`）の認可は「imageable_typeがWorkで、Workが存在するか」
  しか見ておらず、**ログイン済みなら誰でも任意の作品に画像を追加**できた
  → 人気作品の表紙を上書き（デファイス）できる
- 画像削除は「その作品を記録していれば」他人がアップした画像も削除できた

手動登録フローは「Work作成 → 画像アップロード → 記録作成」の順で、画像アップロード時点では
まだ記録が存在しない。このため単純に「記録者のみ許可」にすると手動登録が壊れる。

## 選択肢

### A案: 投稿者列 + 条件付き許可（採用）
- **これは何か:** `images` に投稿者（`user_id`）を持たせ、追加は「記録済み or まだ誰も
  記録・画像を持たない新規作品」のみ、削除は「投稿者本人のみ」に限定する。
- **長所:**
  - 既存の手動登録フロー（記録より先に画像）を変えずに済む
  - 人気作品の表紙上書きと、他人画像の削除を防げる
  - migration 1本（`user_id` 追加）で済む
- **短所:**
  - 画像未登録の外部作品に「最初の1枚」を仕込む余地はわずかに残る（記録が既にある
    作品なら塞げる。影響は限定的）
  - 旧データ（投稿者不明）は後方互換として従来の記録者ルールを残す

### B案: 記録所有者のみに厳格化
- **これは何か:** 画像の追加・削除を「その作品を記録済みのユーザー」に限定し、手動登録を
  「記録を先に作る」順へ変更する。
- **長所:** 認可が単純（記録の有無だけ）
- **短所:** フロントの登録フロー変更が必要（UXに影響）。共同記録作品で他人の画像を
  消せる問題は、結局投稿者列がないと解決できない

### C案: 表示側で緩和（DB変更なし）
- **これは何か:** 認可はそのまま、表紙決定を「最新」→「最初の1枚 or 外部API優先」に変える。
- **長所:** DB変更なしで最小
- **短所:** 「誰でも任意作品に画像追加できる」構造自体は残る（不要画像の追加は可能）。
  表紙を更新したいという本来のUX意図と競合する

## 決定
A案を採用する。

- `images.user_id`（null許可）を追加。以降の投稿は必ず投稿者本人が入る
- **追加の許可条件**: 記録済み作品 or「まだ誰も記録・画像を持たない新規作品」
- **削除の許可条件**: 投稿者本人のみ。旧データ（`user_id` が nil）は後方互換として
  従来ルール（作品の記録所有者）を維持
- 投稿者は paramsからは受け取らず、サーバー側で `current_user` に固定（なりすまし防止）

## 理由
- 手動登録フロー（記録より先に画像）を壊さずに、実害の大きい「人気作品の表紙上書き」と
  「他人画像の削除」を塞げるのがA案だけだった。
- B案はUXフロー変更のコストが高く、C案は構造的な認可欠落が残る。
- 既存画像は投稿者を復元できないため `null` 許可とし、旧データのみ従来ルールで救済する
  （新規画像はすべて投稿者ベースで保護される）。

## 影響
- `images` テーブルに `user_id` 列とインデックス・外部キーを追加。
- `ImagesController#create` は投稿者を固定し、`authorize_imageable!` を条件付き許可に変更。
- `ImagesController#destroy` は投稿者ベースの認可（旧データは記録者フォールバック）に変更。
- 残課題: 画像未登録の外部作品への「最初の1枚」仕込みは残る。必要ならモデレーションや
  「外部API由来の表紙を優先」表示（C案の併用）を将来検討する。
