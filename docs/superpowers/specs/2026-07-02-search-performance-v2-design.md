# 検索パフォーマンス改善 v2 設計書

作成日: 2026-07-02
関連: [2026-03-29-search-performance-design.md](2026-03-29-search-performance-design.md)（v1: 並列化・スケルトンUI・TTL延長 — 実装済み）
関連ADR: [ADR-0042](../../adr/0042-検索の二段階レスポンスに2回リクエスト方式を採用.md)

## 概要

作品検索のキャッシュミス時（＝新しいキーワードで検索したとき）の応答速度を改善する。

- **フェーズA（サーバー側最適化）**: 日本語説明の補完コストを削減する
- **フェーズB（二段階レスポンス）**: 検索結果をまず即表示し、説明の日本語補完を後から反映する

## 現状の問題

v1改善（外部API並列化・補完の5件バッチ並列化・キャッシュTTL 12時間）は実装済み。
キャッシュヒット時は速い（確認済み）が、キャッシュミス時は依然として遅い。

### ボトルネックの内訳

```
1. 外部API並列検索（TMDB/AniList/GoogleBooks/IGDB）
   → 1〜2秒（v1で並列化済み。これ以上の短縮余地は小さい）

2. 日本語説明の補完（enrich_missing_descriptions）★最大のボトルネック
   - 「すべて」検索で最大 50+50+40+50 ≒ 190件の結果が返る
   - 説明が空/英語の結果【全件】が補完対象
   - 1件あたり最大4回のHTTPリクエスト（TMDB×最大3クエリ + Wikipedia）
   - 5件ずつのバッチ並列 → 補完対象100件なら20バッチ
   - 補完系APIのタイムアウトが10秒 → 1件詰まるとバッチ全体が最大10秒待ち
   → 最悪 20〜40秒

3. openBD補完・シリーズ親説明流用・ソート → 軽微
```

### 構造的な無駄

- ユーザーが最初に見るのは上位10〜20件なのに、190件全件を同じコストで補完している
- 「タイトル→日本語説明」は作品固有の情報で検索クエリに依存しないのに、
  検索クエリ単位でしかキャッシュされない（「進撃の巨人」と「進撃」で同じ作品を2回補完する）
- キャッシュキーが生のクエリ文字列のため、末尾空白や全角/半角の揺れで別キャッシュになる

## フェーズA: 補完コストの削減（サーバー側）

対象ファイル: `backend/app/services/work_search_service.rb` と `backend/app/services/external_apis/` 配下

### A-1. 補完対象を上位N件に限定（効果の9割）

```
現在:   fetch(並列) → openBD補完 → 説明補完(全件) → 親説明流用 → ソート → 返す
変更後: fetch(並列) → 一次ソート → 上位N件のみ openBD補完＋説明補完 → 親説明流用 → 最終ソート → 返す
```

- `ENRICHMENT_TOP_N = 20` を定数として定義する（マジックナンバー禁止ルールに従う）
- 一次ソート・最終ソートとも既存の `sort_by_quality_and_popularity`（品質スコア降順→人気度降順）を使う
  - 一次ソートの時点でも画像有無・説明有無は判定できるため、同じ基準で選抜してよい
  - 補完で説明が付くと品質スコアが変わるため、補完後に最終ソートし直す
- `share_series_descriptions`（親説明流用）は全件を対象のままとする
  （HTTPリクエストを伴わないメモリ内処理のため、件数を絞る必要がない）
- 21件目以降は説明が英語/空のまま返ることがある（許容する。補完失敗時と同じ表示になるだけで、既存の表示仕様の範囲内）

### A-2. タイトル単位の補完キャッシュ

補完結果を「検索クエリ」ではなく「作品タイトル」でキャッシュし、クエリをまたいで再利用する。

| キャッシュ | キー | TTL | 備考 |
|-----------|------|-----|------|
| 日本語説明 | `work_search:desc:v1:<正規化タイトル>` | 30日 | 作品の説明文はほぼ変わらないため長期 |
| 説明が見つからなかった事実 | 同上（値に「未発見」マーカーを格納） | 1日 | 毎回4回のHTTP失敗を繰り返さないためのネガティブキャッシュ |
| openBD書誌データ | `work_search:openbd:v1:<ISBN>` | 30日 | ISBNキーなので正規化不要 |

- 「正規化タイトル」は既存の `normalize_for_parent_match` と同じ処理（NFKC＋小文字化＋trim＋連続空白圧縮）を使う
- ネガティブキャッシュの値は `nil` と区別できる形にする（`Rails.cache` は `nil` を「キャッシュなし」と区別できないため、例: 文字列 `'NOT_FOUND'` を定数化して格納する）

### A-3. 検索キャッシュキーの正規化

- `WorkSearchService#search` のキャッシュキー生成時に、クエリへ NFKC正規化＋trim＋小文字化＋連続空白圧縮を適用する
- 外部APIへ送るクエリは trim のみ適用（NFKC/小文字化は各APIの検索精度に影響しうるため変えない）
- `CACHE_VERSION` を `v7` にインクリメントする（キー体系の変更のため）

### A-4. 補完系APIのタイムアウト短縮

- 対象: 補完パスで使うクライアントのみ
  - `WikipediaClient`（説明補完）
  - `OpenbdClient`（書誌補完）
  - `TmdbAdapter#fetch_japanese_description` が使うコネクション
- 変更: `open_timeout: 5, timeout: 10` → `open_timeout: 2, timeout: 3`
- 一次検索（各アダプターの `search`）のタイムアウトは現行（5/10秒）のまま
  - 補完は失敗しても英語のまま表示するだけなので短く攻められるが、
    一次検索の失敗は「結果ゼロ」になるため保守的に維持する
- 実装上の注意: `TmdbAdapter` は検索と補完で同じFaradayコネクションを共有している場合、
  補完専用のタイムアウト設定に分離が必要（コネクション生成をタイムアウト指定可能にする等）

## フェーズB: 二段階レスポンス（2回リクエスト方式）

方式の選定理由は [ADR-0042](../../adr/0042-検索の二段階レスポンスに2回リクエスト方式を採用.md) を参照。
ジョブ基盤・ポーリングは使わず、フロントが2回APIを呼ぶだけで実現する。

### シーケンス

```
フロント                          バックエンド
  │─ ① GET /api/v1/works/search?q=...&enrich=false
  │                                fetch(並列) → 一次ソート → 即返す（1〜2秒）
  │←─ { results: [...], enriched: false }
  │    → 画面に即表示。「説明を取得中…」を表示
  │
  │─ ② GET /api/v1/works/search?q=...（enrichなし＝現行動作）
  │                                補完込みフルパイプライン（フェーズA適用で+1〜3秒）
  │←─ { results: [...], enriched: true }
  │    → 結果を差し替え。「説明を取得中…」を消す
```

### バックエンド仕様

- `GET /api/v1/works/search` に `enrich` クエリパラメータを追加する
  - `enrich=false`: 補完（openBD・説明・親説明流用）をスキップし、fetch＋ソートのみで返す
  - 省略時 / それ以外の値: 現行どおりフル処理（後方互換）
- レスポンスに `enriched`（boolean）フィールドを追加する
- **フルキャッシュ優先**: `enrich=false` でも、まず補完済みフルキャッシュ（`work_search:v7:...`）を確認し、
  ヒットすれば `enriched: true` でそれを返す
  → キャッシュヒット時はフロントが②をスキップでき、リクエスト1回で完結する
- **生結果の短期キャッシュ**: ①で取得した生の検索結果（補完前）を
  `work_search:raw:v7:<media_type>:<正規化クエリ>` に TTL 5分でキャッシュする
  - ②はまず raw キャッシュを確認し、あれば外部API検索をやり直さず補完だけ実行する（二重fetch防止）
  - raw キャッシュも「1件以上あるときのみ書き込む」ルール（空配列の長時間キャッシュ事故防止）に従う
- `enrich=false` のレスポンスはフルキャッシュ（`work_search:v7:...`）には書き込まない（補完前データで汚染しないため）

### フロントエンド仕様

対象: `frontend/src/pages/SearchPage/SearchPage.tsx`、`frontend/src/lib/worksApi.ts`、`frontend/src/lib/types.ts`

- `worksApi.search` に `enrich` オプションを追加し、レスポンス型に `enriched: boolean` を追加する
- 検索実行時のフロー:
  1. `enrich=false` で①を投げ、結果を即表示する（スケルトン→結果カード）
  2. ①のレスポンスが `enriched: true`（フルキャッシュヒット）なら②を省略して完了
  3. `enriched: false` なら「説明を取得中…」の進行表示を出し、②（enrichなし）を投げる
  4. ②の結果で `results` を差し替え、進行表示を消す
- **UI変更点**: 結果一覧の上部に小さなテキスト＋スピナーの進行表示（「日本語の説明を取得中…」）を追加する
  - 既存の `SearchProgress` コンポーネントの流用または軽量版を使う
  - `WorkCard` 自体は変更しない
  - スタイル値は `tokens.css` のCSS変数のみ使用（ハードコード禁止）
- **キャンセル制御**: 新しい検索・ジャンル変更時は①②両方のリクエストを `AbortController` で中断する
  （①用・②用で同一の controller を共有してよい）
- **②失敗時のフォールバック**: ②がエラーになっても①の結果を表示したままにし、
  エラーメッセージは出さない。進行表示だけ消す（速報結果で十分機能するため）
- 差し替えで件数・順序が変わりうることは許容する（補完で品質スコアが変わり最終ソートが動くため）
- `handleSearch`（フォーム送信）と `handleGenreChange`（ジャンル変更）の検索ロジックは
  現在ほぼ重複しているため、この機会に共通関数へ抽出する（二段階化でさらに複雑になるのを防ぐ）
- analytics（`SEARCH_PERFORMED`）は②完了時（または②省略時は①完了時）に1回だけ送る

## 改善効果の見込み

| シナリオ | 現在 | 改善後 |
|---------|------|--------|
| 初回検索: 結果が見えるまで | 20〜40秒（最悪） | **1〜2秒**（速報表示） |
| 初回検索: 説明の日本語化完了まで | 20〜40秒（最悪） | 2〜5秒（上位20件限定＋タイトルキャッシュ＋タイムアウト短縮） |
| 類似クエリの2回目（別キーワード・同じ作品群） | 20〜40秒 | 1〜3秒（タイトル単位キャッシュが効く） |
| 同一クエリの2回目（フルキャッシュヒット） | 即座 | 即座（リクエスト1回で完結） |

## テスト方針

### バックエンド（RSpec）

- `WorkSearchService`:
  - 補完対象が上位 `ENRICHMENT_TOP_N` 件に限定されること（21件目以降に補完のHTTP呼び出しが発生しない）
  - タイトル単位キャッシュ: 同一タイトルの2回目の補完で外部APIを呼ばないこと
  - ネガティブキャッシュ: 「未発見」がキャッシュされ、TTL内は再試行しないこと
  - キャッシュキー正規化: 末尾空白・全角空白・大文字小文字の揺れで同一キャッシュにヒットすること
- request spec（`works_controller`）:
  - `enrich=false` で `enriched: false` と補完スキップの結果が返ること
  - `enrich=false` でもフルキャッシュヒット時は `enriched: true` で返ること
  - `enrich` 省略時は現行どおり（後方互換）であること
  - 認証チェックが引き続き効いていること

### フロントエンド（Vitest + RTL）

- 二段階表示: ①の結果が即表示され、②の結果で差し替わること
- `enriched: true`（キャッシュヒット）時に②が発行されないこと
- 「説明を取得中…」が②の実行中のみ表示されること
- ②失敗時に①の結果が残り、エラーが表示されないこと
- 新しい検索開始時に進行中の①②が中断されること
