# CLAUDE.md バイブコーディング移行 設計仕様

## 概要

RecollyプロジェクトをClaude Code主体の「完全バイブコーディング」スタイルに移行するための
グローバル・プロジェクトCLAUDE.md変更仕様。

**決定日**: 2026-05-09

---

## 背景・目的

IKさんは転職ポートフォリオとしてRecollyを開発中。
これまでの「学びながら実装する」スタイルから、
「Claude Codeに実装を任せ、IKさんは製品判断に集中する」スタイルへ移行する。

---

## 変更対象

- `~/.claude/CLAUDE.md`（グローバル設定）
- `D:\Dev\recolly\CLAUDE.md`（プロジェクト設定）

---

## グローバルCLAUDE.md の変更

### 削除するセクション

- 「原則: ソクラテス式対話」全体
- ルール1（専門用語の初出説明ルール）
- ルール2（なぜそうするかを添えるルール）
- ルール3（作業の全体像を最初に示すルール）
- ルール4（選択肢のメリデメ説明ルール）→ 判断場面でのみ適用する形に変更
- ルール5（コマンドへの解説添付ルール）

### 追加するセクション

```
## 説明・対話ルール（バイブコーディング前提）

Claude Codeが実装を担当する。IKさんは製品判断のみ行う。
説明は「判断に必要なとき」だけ行い、実装の詳細は原則説明しない。

### 説明が必要な場面
- 設計の選択肢がある（AとBどちらにするか）
- UIの変更が見た目に大きく影響する
- DBやAPIの設計が変わる（後から変えにくいもの）

### 説明のスタイル
- 専門用語は避けるか、出てきたら括弧で一言補足
- 選択肢はメリット・デメリットを平易な言葉で（例え話OK）
- 「決めてください」ではなく「こうしたいですが、よいですか？」で確認

### 説明しない場面
- 実装の詳細（どのファイルに何を書くか等）
- コマンドの解説
- 新しい技術の仕組み
```

## プロジェクトCLAUDE.md の変更

### 変更するセクション: 「開発手法」

**変更前**: SDD+TDD+Issue駆動（全機能に一律適用）＋ comprehension-guard/learning-note の自動発動

**変更後**:

```
## 開発スタイル：バイブコーディング（Claude Code主体）

Claude Codeがすべての実装を担当する。
IKさんは製品・設計の判断のみ行う。

### ワークフロー（機能規模で3段階）

| 規模 | 判断基準 | プロセス |
|------|---------|---------|
| 大 | 新機能・画面追加・DB変更 | 仕様書 → 計画 → TDD → PR |
| 小 | 既存機能の改善・軽微な変更 | Issue → 実装 → PR |
| 修正 | バグ修正・コピー変更等 | 直接実装 → PR |

### IKさんが判断する場面（Claude は必ず確認を取る）

1. **UIデザインの変更** — コンポーネントの追加・見た目の大きな変更
2. **PRのマージ・本番デプロイ** — IKさんが承認して初めて実行

### 自動発動スキル

| スキル | 発動条件 |
|--------|---------|
| `adr` | 設計判断が確定したとき（聞かずに自動作成） |
```

**削除する自動発動ルール**:
- `comprehension-guard` の自動発動
- `learning-note` の自動発動

---

## 判断記録

| 項目 | 決定内容 | 理由 |
|------|---------|------|
| ソクラテス式対話 | 廃止 | バイブコーディングでは学習より開発速度を優先 |
| comprehension-guard | 廃止 | 技術選定の理解負債より実装速度を優先 |
| learning-note | 廃止 | 同上 |
| ワークフロー | 規模別3段階 | 全機能に同じプロセスは非効率 |
| UI変更確認 | 必須 | 見た目は最終的にIKさんの判断が必要 |
| PR/デプロイ確認 | 必須 | 本番への影響は必ずIKさんが承認する |
| adr | 維持 | 設計判断の記録は将来の参照価値が高い |
