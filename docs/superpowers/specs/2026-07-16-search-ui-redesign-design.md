# 検索UI再設計（ジャケット主体グリッド＋記録時補完） 設計書

作成日: 2026-07-16
関連: [2026-07-02-search-performance-v2-design.md](2026-07-02-search-performance-v2-design.md)（v2: 補完コスト削減・二段階レスポンス）
関連ADR: [ADR-0042](../../adr/0042-検索の二段階レスポンスに2回リクエスト方式を採用.md)（廃止）・[ADR-0043](../../adr/0043-検索の二段階レスポンスを廃止し1回リクエストに戻す.md)

## 概要

検索結果カードから説明文を廃止し、「ジャケット画像＋ジャンル＋タイトル＋記録ボタン」のグリッドUIに作り直す。
日本語説明の補完は検索時ではなく「記録する」時に1作品分だけ実行する。

## 背景・経緯

1. 検索の遅さの根本原因は「検索結果20件分の日本語説明補完」（1件あたり最大4回のHTTP）だった
2. ADR-0042の二段階レスポンスは体感を隠したが、英語説明が一瞬表示される問題があった
3. ADR-0043で二段階を廃止したところ、今度は素の遅さ（全ジャンル検索で30秒級）が露出した
4. **「そもそも検索結果に説明文は必要か」を問い直した結果、検索カードには不要と判断**
   - 作品の識別はジャケット画像＋タイトルで足りる（Annict・読書メーター等も同様の構成）
   - 説明文が本当に必要なのは作品詳細ページであり、それは記録済み作品にしか存在しない

## 決定事項（2026-07-16 IKさん承認）

| 論点 | 決定 |
|------|------|
| 検索カードの表示内容 | ジャケット・ジャンルバッジ・タイトル・記録ボタンのみ（説明文なし） |
| レイアウト | グリッド（ジャケット主体の縦カード） |
| 日本語説明の補完時期 | 「記録する」時に1作品分だけ同期実行 |
| PR分割 | 先行作業分（説明文日本語のみ化・ラベル削除・バックエンド高速化・docker修正）とまとめて1PR |

## UI仕様

### 検索結果グリッド

```
┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐
│     │ │     │ │     │ │     │
│ジャケ │ │ジャケ │ │ジャケ │ │ジャケ │
│     │ │     │ │     │ │     │
├─────┤ ├─────┤ ├─────┤ ├─────┤
│アニメ │ │映画  │ │ゲーム │ │本   │
│タイトル│ │タイトル│ │タイトル│ │タイトル│
│[記録] │ │[記録] │ │[記録] │ │[記録] │
└─────┘ └─────┘ └─────┘ └─────┘
```

- **WorkCard を縦型カードに作り直す**
  - ジャケット画像: アスペクト比 2:3（書影・ポスターの標準）。画像なしはプレースホルダー
  - ジャンルバッジ: 既存のメディアタイプ別色（`--color-anime` 等）を維持
  - タイトル: 2行まで表示し溢れは省略（line-clamp: 2）
  - アクション: `記録する` ボタン / `記録済み` 表示 / ローディング中 `記録中...`（既存仕様維持）
  - 説明文・「※ シリーズ全体の説明」注釈は表示しない
- **列数（ADR-0026の3段階ブレークポイント準拠）**
  - PC: 5列 / タブレット(〜768px): 4列 / モバイル(〜480px): 3列（2026-07-16 IKさん確認でPC5列に決定）
  - CSS Grid + `gap: var(--spacing-md)` で実装
- **SearchSkeleton をグリッド形状に更新**（縦カードのシマーを列数分表示）
- **SearchProgress（3段階メッセージ）は維持**（検索自体は数秒かかるため）
- ゲーム英語検索ヒント・手動登録フォーム・RecordModal は現状維持
- DESIGN.md 準拠: tokens.css の変数のみ使用・`<Button>` 等の共通コンポーネント使用

## バックエンド仕様

### 検索パスの簡素化（WorkSearchService）

```
現在:   fetch(並列) → 一次ソート → 上位20件 openBD補完＋説明補完 → 親説明流用 → 最終ソート
変更後: fetch(並列) → 一次ソート → 上位20件 openBDカバー補完のみ → 最終ソート
```

- **説明補完（TMDB×3クエリ＋Wikipedia）を検索パスから撤去**（最大のボトルネック）
- **openBDカバー補完は検索時に残す**: グリッドUIはジャケットが主役であり、
  Google Books結果は書影欠損が多くopenBDで埋めているため（1件1HTTP・30日キャッシュ・軽い）
- シリーズ親説明の流用（`share_series_descriptions`）と `description_from_parent` フラグは廃止
  （検索結果に説明を出さないため不要になる）
- `enrich` パラメータ・`enriched` レスポンスフィールド・`Outcome`・rawキャッシュ（5分）を廃止し、
  検索は常に単一パス・単一キャッシュにする
- `CACHE_VERSION` を `v8` にインクリメント
- 品質スコア（画像0.5＋説明0.5）は現状維持（生APIの説明有無は情報量の指標として引き続き有効）

### 記録時の説明補完（新規）

- `Records#create` で外部API由来のWorkを作成した直後、説明が空または英語なら
  その1作品の日本語説明を同期取得してWorkに保存する
- 補完ロジックは `WorkEnrichmentService` の既存処理（タイトル単位30日キャッシュ・
  TMDB→Wikipediaの順・NOT_FOUNDネガティブキャッシュ）を単一作品向けに再利用する
- 所要時間: キャッシュヒット時は即時、ミス時は典型1〜3秒（記録ボタンの既存ローディングUIで吸収）
- 補完失敗時は説明なし/英語のまま保存する（記録自体は失敗させない）
- 既存Workの再利用時（`find_or_create_by` で既存ヒット）も説明が空/英語なら補完を試みる

### APIの変更

| エンドポイント | 変更 |
|---------------|------|
| `GET /api/v1/works/search` | `enrich` パラメータ廃止・レスポンスから `enriched` を削除（`{ results: [...] }` のみ） |
| `POST /api/v1/records` | 外部仕様変更なし（内部で説明補完が走る） |

## テスト方針

- バックエンド: 検索が説明補完を行わないこと / openBDカバー補完は行うこと /
  記録作成で説明補完が走ること（キャッシュヒット・ミス・失敗時） / enrichパラメータ廃止
- フロントエンド: グリッドカードの表示要素（画像・バッジ・タイトル・ボタン） /
  説明文が表示されないこと / 既存の検索フロー（キャンセル・エラー・記録済み）の回帰

## 既知のトレードオフ

- 検索結果から作品の内容（あらすじ）を確認できなくなる。識別はジャケット＋タイトルに依存する
- 記録操作が説明補完の分だけ長くなることがある（典型1〜3秒。既存のローディングUIで表現）
- シリーズ親説明の流用がなくなるため、記録時補完で日本語説明が見つからないシリーズ子作品
  （Season 2等）は詳細ページの説明が英語または空になることがある
