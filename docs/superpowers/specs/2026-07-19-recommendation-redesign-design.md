# レコメンド機能の再設計（精度向上＋ジャンル横断化）

日付: 2026-07-19
ステータス: 承認済み

## 背景・問題

現状のレコメンドには4つの問題がある。

1. **「◯◯好きにおすすめの他メディア」枠が常に空**
   `MediaPreferencePromptBuilder`がAIに`media_type`を日本語ラベル（アニメ、映画…）で出力させているが、`WorkSearchService`のアダプター表は英語キー（`anime`等）のため、検索アダプターが1つも選ばれず結果が常に0件になる。

2. **メディアタブが「分析中…」のまま放置される**
   `MediaPreferenceProfilesController#index`はプロファイル未生成時に`generating`を返すだけで分析ジョブを起動しない。全体おすすめが生成済みの状態で後からメディアが記録3件に達しても、手動更新するまで永遠に「分析中…」。

3. **OVA・特別篇・CMがおすすめされる**
   `WorkRecommender#find_best_match`は検索結果から「未記録の最初の1件」を採用する。AIが本編（例: Steins;Gate）を提案→本編は記録済みでスキップ→検索結果の次に並ぶ特別篇・OVA・CM（例: 聡明叡智のコグニティブ・コンピューティング）が採用される。良い作品を見ている人ほど派生データがおすすめされる構造。

4. **ジャンル横断レコメンドが存在しない（コンセプトとの乖離）**
   メディアタブは「そのメディアの記録が3件以上」ないと何も出ない。Recollyのコンセプトは「ジャンル横断で作品を楽しむ」なので、アニメしか見ない人にもアニメの記録から映画・ドラマをおすすめできるべき。

## 決定事項（IK承認済み）

- 生成方式は**一括生成**: AI呼び出しは更新1回につき1回。全記録を入力し、総合分析＋全メディア分のおすすめを一度に出力する
- モデルは**Sonnet（claude-sonnet-5）に格上げ**: 呼び出し回数が7回→1回に減るため、総コストは現状より下がる見込み
- 各メディアタブは記録0件でも「全記録から推定したそのメディアのおすすめ」を常に表示する
- cross_media枠（他メディアおすすめセクション）と総合タブの作品リスト（おすすめ7件＋挑戦3件）は廃止

## 設計

### 1. 一括生成アーキテクチャ

`PreferenceAnalyzer`＋`PreferencePromptBuilder`を改修し、1回のClaude API呼び出しで以下を出力させる。

```json
{
  "summary": "総合の好み傾向分析（200字程度）",
  "preference_scores": [{ "label": "嗜好の軸名", "score": 1.0〜10.0 }],
  "media_recommendations": {
    "anime":  { "trend": "このメディアでの傾向・推薦方針（1〜2文）", "works": [{ "query": "作品タイトル", "reason": "おすすめ理由" }] },
    "movie":  { "...": "全6メディア分" }
  }
}
```

- 入力: 全メディアの記録データ（ジャンル別統計・高評価TOP10・断念作品・タグ統計・感想抜粋・お気に入り）＋**記録済み全作品タイトル一覧**（後述の除外指示用）
- `works`は各メディア**8件**提案させ、検索での実在確認を通過した上位**5件**を採用（検索で落ちる分の保険）
- モデル: `claude-sonnet-5`、`max_tokens: 16000`（thinkingトークンと本文の合計上限のため）
- 発動条件: 全体の記録が5件以上（`PreferenceAnalyzer::MINIMUM_RECORDS`を維持）。メディア別の「3件以上」条件は撤廃
- JSONパース失敗時は1回リトライし、それでも失敗したらエラーログを残して既存データを保持

### 2. データモデル

既存テーブルを流用し、一括生成の結果を分配保存する。

- `Recommendation`（総合）: `analysis_summary` / `preference_scores` / `genre_stats` / `top_tags` を保存。`recommended_works` / `challenge_works` カラムは**マイグレーションで削除**
- `MediaPreferenceProfile`（メディア別・6行）: `analysis_summary`（←trend文）/ `same_media_works`（←採用5件）を保存。`cross_media_works` / `preference_scores` / `top_tags` カラムは**マイグレーションで削除**
- メディア別の嗜好スコアは廃止（一括出力の肥大化を防ぐ。メディア別カードは傾向文のみ表示）

### 3. ジョブ・API

- `RecommendationRefreshJob`に一本化。1回の実行で総合＋全メディア分を保存する。`MediaProfileRefreshJob`は**削除**
- `MediaPreferenceProfilesController#index`: プロファイル未生成（かつ全体記録5件以上）のとき`generating`を返しつつ`RecommendationRefreshJob`を起動する（放置バグの解消）。多重起動防止のため、`Rails.cache`にユーザー単位の起動済みフラグ（TTL 10分）を置き、フラグがある間は再起動しない
- レスポンスの`status`体系:
  - 全体記録0件 → `no_records`
  - 全体記録1〜4件 → `insufficient_records`（必要件数は全体5件に統一）
  - 生成中 → `generating`
  - 生成済み → `ready`（記録0件のメディアタブにも`ready`でおすすめが返る）

### 4. OVA/特別篇/CM混入対策（WorkRecommender改修）

2段構えで対策する。

1. **formatフィルタ**: AniListの`format`が `SPECIAL` / `OVA` / `MUSIC` / `TV_SHORT` の作品はレコメンド採用から除外する。`ONA`はNetflixアニメ等の本編が多いため除外しない。
   - 前提: `AnilistAdapter#build_metadata`に`format`を追加する（GraphQLでは取得済みだが未保存）。検索キャッシュの`CACHE_VERSION`をv13に上げる
2. **既記録スキップ**: 「未記録の最初の1件を採用」をやめる。検索結果の最上位（`SearchRelevanceScorer`のティアが最高の候補）が既記録なら、その提案キーワード自体をスキップして次の提案へ進む。派生作品への繰り下げ採用をしない
3. **プロンプトでの除外指示**: 記録済み全作品タイトル一覧をプロンプトに含め、「これらとその派生作品（OVA・特別篇・劇場版総集編等）は提案しない」と明示する

※formatフィルタは検索機能全体には適用せず、レコメンド採用判定（`WorkRecommender`側）のみに適用する。通常検索でOVA等を探せる機能は維持する。

### 5. フロントエンド

- メディア別タブ: `cross_media_works`セクションを削除。記録0件でも`same_media_works`（おすすめ5件）と傾向文を表示。「あと◯件で分析できます」の進捗カードはメディア別条件の撤廃に伴い削除し、全体5件未満のときの案内は総合タブ側に集約
- `MediaAnalysisSummaryCard`: 嗜好スコア表示を削除し、傾向文のみのシンプルなカードにする
- 総合タブ: 分析サマリー＋嗜好スコア＋ジャンル統計の「分析ダッシュボード」に整理。作品リスト（おすすめ・挑戦）は削除
- 型定義（`mediaPreferenceProfile.ts` / `recommendation.ts`）をAPI変更に合わせて更新

### 6. テスト方針

TDD（Red-Green-Refactor）で進める。主なテスト対象:

- プロンプトビルダー: 一括生成用プロンプトの構造（記録済みタイトル一覧・6メディア分の出力指示を含む）
- レスポンス分配保存: 一括JSONから`Recommendation`＋`MediaPreferenceProfile`6行への保存
- formatフィルタ: SPECIAL/OVA/MUSIC/TV_SHORTの除外、ONA/TV/MOVIEの通過
- 既記録スキップ: 最上位候補が既記録のときキーワードごとスキップされること
- パース失敗リトライ: 1回リトライ後の失敗で既存データが保持されること
- コントローラー: `generating`時のジョブ自動起動、記録0件メディアの`ready`レスポンス
- フロント: タブ表示の新ステータス分岐（Vitest）

## スコープ外

- 埋め込みベース・協調フィルタリング等の機械学習的アプローチ（個人開発の規模に対して過剰）
- 検索機能全体へのformatフィルタ適用（レコメンド採用判定のみ）
- 旧`MediaProfileRefreshJob`のキュー内残留ジョブへの互換対応（デプロイ時にキューが空であることを確認する運用で対応）

## 懸念点（承知の上で進める）

- 記録0件のメディアのおすすめは精度が読みにくい（アニメの好みから本を推定するのは難易度が高い）。傾向文で「なぜこの推薦か」を補足することで納得感を担保する
- 一括出力はJSONが大きくなるため出力崩れのリスクがある。リトライ1回＋失敗時は既存データ保持で緩和する
